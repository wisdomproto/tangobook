# 탱고 보드 — 카메라 인식 설계

2026-08-26 기획 · 2026-08-28 갱신(§11 = 실물 형상·잠망경·거치 확정)

판과 블록은 지금 그대로 두고, **센서 대신 스마트폰 카메라로** 판 위의 한글 블록을
읽는다. 3D 보드는 그 인식기를 시험할 시뮬레이터로 쓴다.

---

## 1. 왜 이걸 하나

지금 탱고보드는 판 안에 센서 PCB(377×240mm)와 메인 PCB, 배터리, 스피커가 들어간다.
블록마다 PCB도 들어간다. 인식을 카메라가 대신하면 **판은 사출물, 블록도 사출물**만
남는다 — 전자 부품이 통째로 빠진다.

대신 인식 난이도가 하드웨어에서 소프트웨어로 옮겨온다. 그 난이도가 감당 가능한지를
**만들기 전에** 재는 것이 이 문서의 목적이다.

## 2. 이 문제가 쉬운 이유 — 판이 이미 캘리브레이션 타겟이다

일반적인 "사진에서 물체 인식"이 아니다. 우리에겐 세 가지 강한 제약이 있다.

**① 판에 15mm 격자로 핀이 촘촘히 박혀 있다.** 놀이 영역 321×216mm 안에 21×14칸.
이건 체스보드 캘리브레이션 패턴과 같은 성질이라, 평면 자세(호모그래피) 추정에 이상적이다.
카메라가 어떤 각도에 있든 격자만 잡으면 판 좌표계로 되돌릴 수 있다.

**② 블록이 놓일 수 있는 위치가 격자로 이산화되어 있다.** 연속 좌표를 맞출 필요가 없다.
294칸 중 어디냐만 정하면 되고, 반 칸 오차는 반올림이 흡수한다.

**③ 블록 종류가 23개, 회전이 최대 4방향.** 후보가 유한하고 작다. 게다가 각 블록은
크기가 정해져 있다(3×3 = 45mm, 2×5 = 30×75mm …).

이 셋 때문에 **딥러닝이 필요 없다.** 고전 컴퓨터 비전 — 평면 호모그래피 + 색 분할 +
템플릿 매칭 — 으로 충분하고, 그편이 학습 데이터도 필요 없고 오작동을 설명할 수 있다.

## 3. 실행 환경

**폰 웹브라우저**로 결정. `getUserMedia` → `<canvas>` → 온디바이스 처리.
설치가 없고, 탱고북이 이미 웹 PWA라 결이 맞고, 무엇보다 **시뮬레이터와 인식기가 같은
코드를 공유**한다 — 3D가 렌더한 프레임을 실제 카메라 프레임과 똑같이 먹일 수 있다.

영상이 기기 밖으로 나가지 않는다는 점도 중요하다. 아이 얼굴이 찍힐 수 있는 영상이다.

### OpenCV.js 를 쓰나

쓴다. 필요한 건 다섯 개뿐이다.

| 쓰임 | 함수 |
|---|---|
| 판 테두리 찾기 | `findContours` + `approxPolyDP` |
| 판 좌표계로 되돌리기 | `findHomography` + `warpPerspective` |
| 블록 색 분리 | `cvtColor`(HSV) + `inRange` |
| 블록 덩어리 나누기 | `connectedComponentsWithStats` |
| 자모 맞히기 | 직접 짠 IoU 매칭 (OpenCV 불필요) |

전체 빌드는 8MB대라 무겁다. **필요한 모듈만 커스텀 빌드하면 1~2MB.** 그것도 부담이면
호모그래피(8×8 선형계)와 warp는 직접 짤 수 있고, warp는 오히려 **이미 있는 WebGL
셰이더로 하면 공짜**다. 다만 v1은 OpenCV.js로 빨리 만들고, 느리면 그때 이식한다.

## 4. 파이프라인

```
카메라 프레임
  ↓ ① 판 검출        테두리 사각형 → 네 꼭짓점
  ↓ ② 자세 추정      호모그래피 (격자 핀으로 정밀화)
  ↓ ③ 정사영 warp    판 좌표계 = mm, 격자가 정확히 15px 배수
  ↓ ④ 블록 분리      HSV 2색 마스크 → 연결요소
  ↓ ⑤ 자모 분류      칸 스냅 + 회전 추정 + 템플릿 IoU
  ↓
{ch, x, y, w, h}[] → parseFree() → "가지"
```

**⑤ 다음은 이미 있다.** `parseFree` 는 2D 시뮬레이터에서 검증됐고 3D에도 그대로 들어가
있다. 카메라 인식기가 할 일은 **그 함수가 먹는 형식까지 만들어 주는 것**뿐이다.
이게 설계의 핵심 이음매다.

### ① 판 검출

판 테두리(프레임)는 놀이 영역보다 밝고, 큰 사각형 하나다. 화면에서 가장 큰
4각 컨투어를 고른다. 실패하면 격자 핀 패턴 자체를 `findCirclesGrid` 로 찾는 폴백.

### ② 자세 추정 — 격자 핀으로 정밀화

네 꼭짓점만으로 구한 호모그래피는 렌즈 왜곡과 검출 오차가 남는다.
warp 후 **격자 핀이 예상 위치에 오는지** 보고 잔차로 다시 맞춘다.
핀이 294개라 과결정계이고, 이게 정확도의 대부분을 만든다.

### ③ warp — 여기서 문제가 2D로 축소된다

warp 결과는 항상 같은 크기(예: 판 1mm = 3px → 963×648)다. 카메라가 어디 있었든
이 시점부터는 **정면에서 본 판**만 다룬다. 뒤 단계가 각도와 무관해진다.

### ④ 블록 분리 — 자음/모음 2색

색은 자음·모음 2종으로 확정. 색만으로 자모를 가릴 수는 없지만,
**판(회색)에서 블록을 떼어내는 데는 2색으로 충분**하다.
🔴 두 색은 채도를 높게, 서로 색상환에서 멀게 고른다. 판이 무채색이라 채도 하나로
전경/배경이 갈린다 — 조명 색온도가 흔들려도 채도는 비교적 버틴다.

### ⑤ 자모 분류 — 템플릿 IoU

warp 후 블록은 정면이고 크기가 정해져 있으며 회전은 4방향뿐이다.
**자모 20여 종 × 회전 = 80개 이진 마스크**를 미리 굽고, 검출된 덩어리와 IoU 최대를 고른다.

이 템플릿은 **새로 그릴 필요가 없다** — 3D 블록을 만드는 그 획 좌표
(`CATALOG` 의 `paths`/`circles`)를 위에서 내려다본 2D로 래스터화하면 그대로 템플릿이다.
즉 **모델과 인식기가 같은 한 벌의 좌표를 공유**한다. 블록 도면이 바뀌면 양쪽이 같이 바뀐다.

## 5. 거치대 조건 — 시뮬레이터 실측

🔴 **처음 계산은 2.5배 낙관적이었다.** "판이 화면에 꽉 찬다"고 가정했는데, 실제 거치
조건에서는 그렇지 않다. 높이 300mm에 경사 30°면 카메라가 판에서 600mm 떨어지고,
그 거리의 화각 폭이 810mm라 **판이 화면의 40%밖에 차지하지 않는다.**

시뮬레이터에서 1080px 폭으로 렌더해 실제로 잰 값 (FOV 68°):

| 경사각 / 높이 | 격자 한 칸 | 획(13mm) | 판정 |
|---|---|---|---|
| 20° / 300mm | 5px | 4px | ✗ 자모 구분 불가 |
| 30° / 300mm | 10px | 9px | ✗ 부족 |
| 45° / 300mm | 20px | 17px | △ 경계 |
| **45° / 250mm** | 24px | **21px** | ✓ |
| 60° / 350mm | 26px | 22px | ✓ |

### 인식기를 붙여 실제로 재 본 결과 (2단계 완료)

낱말 「가지」를 판에 완성해 두고 거치 조건을 흔들었다. 채점은 정답(`placed`)과 자동 대조.

| 경사 / 높이 / 방위 | 인식 | 블록 |
|---|---|---|
| 75° / 250 / 0 | 가지 ✓ | 4/4 |
| 60° / 280 / 0 | 가지 ✓ | 4/4 |
| 50° / 250 / 0 | 가지 ✓ | 4/4 |
| 45° / 250 / 0 | 가지 ✓ | 4/4 |
| 45° / 300 / 0 | 가지 ✓ | 4/4 |
| **35° / 300 / 0** | **가지 ✓** | 3/4 |
| 30° / 300 / 0 | 가리 ✗ | 3/4 |
| 25° / 250 / 0 | 가 ✗ | 3/4 |
| 45° / 250 / **+25** | 가지 ✓ | 4/4 |
| 45° / 250 / **−25** | 가지 ✓ | 4/4 |
| 60° / 400 / +15 | 가지 ✓ | 4/4 |
| 70° / 350 / −15 | 가지 ✓ | 4/4 |

**경계는 35°다.** 픽셀 수로 잡은 초기 권고(45°)보다 관대하다 — 획이 좀 뭉개져도
템플릿 IoU 가 버틴다. **방위각 ±25° 는 영향이 없다** — 판을 비뚤게 놓아도 된다.
한 프레임 처리 **1~7ms**.

🔴 **정확도의 대부분은 블록 옆면을 떼는 데서 나왔다.** 두께 8mm 의 옆면이 획에 붙으면
ㅏ(획 폭 2칸)가 ㅒ(3칸)로, ㄷ 이 ㅌ 으로 넘어간다. 윗면은 밝고 옆면은 어두워
명도 임계 하나로 갈리며, 그것만으로 30°/300mm 가 **1/4 → 4/4** 로 올랐다.
⚠️ 지금 임계(0.70)는 시뮬레이터 조명 기준이다. 실제 카메라에선 덩어리별 적응 임계가 필요하다.

~~**권고: 경사 35° 이상, 높이 250~400mm, 방위각 자유.**~~
→ 300 조합 스윕으로 갱신됨(아래 3단계): **경사 55° 이상 권장, 40° 이상 실용.**

### 2b 판 검출 — 외곽 4점으로는 부족하다 (실측)

화면에서 판을 찾는 것 자체는 쉬웠다. 명도가 **배경 0.10 / 프레임 0.42 / 판 0.70** 으로
깨끗이 갈려서, 임계 0.40 이면 판이 한 덩어리로 잡힌다(0.55 로 자르면 프레임이 빠지며
세 조각으로 쪼개진다). 모서리는 극점 대신 **네 변을 직선으로 맞춰 교점**을 쓴다 —
극점만 쓰면 모서리 라운드(R12)에 수십 px 씩 먹힌다.

문제는 정밀도다.

| 조건 | 판이 화면에 | 모서리 오차 | 블록 |
|---|---|---|---|
| 75° / 250 | 넘침 | 204px | 0/4 |
| 45° / 250 | 넘침 | 94px | 0/4 |
| 45° / 300 | 들어옴 | 28px | 1/4 |
| 35° / 300 | 들어옴 | 30px | 1/4 |
| 30° / 300 | 들어옴 | 23px | 1/4 |
| 40° / 400 | 들어옴 | 21px | 1/4 |
| 35° / 400 / az15 | 들어옴 | 101px | 0/4 |

🔴 **판이 화면 밖으로 나가면 변 피팅이 화면 경계를 판 모서리로 착각한다.**
카메라 거리는 `height / sin θ` 라 각도가 높을수록 가까워지고, 75°/250mm 면
화각 폭 349mm 에 판 493mm 라 애초에 안 들어온다. → 실루엣이 화면 가장자리에 닿으면
검출을 거부하도록 막았다. 실제 앱에서도 「판이 다 보이게 놓아주세요」로 안내할 상황이다.

🔴 **판이 다 들어와도 오차 21~30px 가 남고, 그걸로는 인식이 안 된다.**
21px 은 놀이 영역에서 약 6mm — 격자 15mm 의 40%라 칸 반올림이 틀린다.
방위각이 붙으면 100px 넘게 벌어진다(변 피팅이 회전에 약하다).

**→ 외곽 4점 방식은 원리적으로 부족하다. §4 ②에 적어 둔 격자 핀 정밀화가 필요하다.**
핀이 294개라 과결정계이고, 그게 정확도의 대부분을 만든다는 처음 판단이 맞았다.
지금은 검출 실패 시 정답 좌표로 물러서므로 뒷단(색 분리·자모 분류)은 계속 4/4 로 돈다.

### 2c 격자 핀 정밀화 — 핀은 보인다, 다만 해상도가 있어야 한다

핀을 찾으려면 먼저 핀이 보여야 한다. 처음엔 안 보였다.

🔴 **1080px 에서는 핀이 3~4px 로 뭉개져 명도 변동이 1% 미만, 주기도 없다.**
보수적으로 잡은 시뮬 해상도가 오히려 이 단계를 원리적으로 불가능하게 만들고 있었다.
**2160px 으로 올리니 프로파일에 주기가 또렷하게 나온다**(진폭 0.75%).
요즘 폰 카메라는 4000px 급이라 2160 도 여전히 보수적이다. → 시뮬 해상도를 2160 으로 올렸다.

그리고 그 주기가 결정적인 증거를 줬다.

**검출된 주기 39px vs 기대값 48px — warp 스케일이 19% 어긋나 있다.**
블록이 칸을 통째로 벗어나니 위치가 맞을 수가 없다. 2b 의 오차 21~30px 이
왜 인식을 무너뜨렸는지가 이 숫자로 설명된다.

**정밀화 방법도 이 발견이 정해 준다.** 4점을 다시 추정할 필요 없이,
warp 이미지의 x·y 프로파일에서 **주기와 위상**만 찾으면 된다 —
스케일 2 + 오프셋 2, 네 파라미터. warp 후에는 원근이 이미 제거돼 있어
주기가 균일해야 하고, 균일하지 않은 만큼이 곧 호모그래피 오차다.

⚠️ 놀이 영역을 명도로 직접 찾는 방법도 시도했으나 조건마다 다르게 쪼개져 못 쓴다.

### 2d 주기·위상 보정 — 방위각 0 에서 전 구간 성공

warp 이미지의 x·y 명도 프로파일을 CELL 근처 단일 주파수 DFT 로 훑어 **주기와 위상**을
찾고, 그만큼 호모그래피를 스케일·평행이동한다(네 파라미터). 판 표면만 보도록
채도 있는 픽셀(블록)은 프로파일에서 뺀다. 핀이 밝은지 어두운지 모르므로 위상 후보
둘을 다 만들어 인식이 잘 되는 쪽을 고른다 — 인식이 1~7ms 라 두 번 돌려도 싸다.

| 경사 / 높이 / 방위 | 낱말 | 블록 |
|---|---|---|
| 55° / 400 / 0 | 가지 ✓ | 4/4 |
| 50° / 350 / 0 | 가지 ✓ | 4/4 |
| 45° / 350 / 0 | 가지 ✓ | 4/4 |
| 40° / 400 / 0 | 가지 ✓ | 3/4 |
| 35° / 400 / 0 | 가지 ✓ | 2/4 |
| 30° / 450 / 0 | 가지 ✓ | 2/4 |
| 45° / 400 / **+15** | ✗ | 1/4 |
| 45° / 400 / **−15** | ✗ | 1/4 |
| 40° / 450 / **+25** | ✗ | 0/4 |

**정밀화가 결정적이다** — 같은 조건에서 끄면 「개」, 켜면 「가지」.

🔴 **블록 지표는 「밀린 것」과 「틀린 것」을 나눠 세야 한다.** 격자 원점이 통째로
한두 칸 밀려도 상대 배치가 맞으면 낱말은 맞는다. 실제로 인식이 `ㄱ@1,2 ㅏ@4,2 ㅈ@7,2`,
정답이 `ㄱ@2,4 ㅏ@5,4 ㅈ@8,4` 로 **정확히 (−1,−2) 평행이동**이었다. 절대 위치만 보면
0/4 라 파이프라인이 망가진 것처럼 보이지만, 낱말은 맞는다. 채점을 둘로 갈랐다.

🔴 **남은 벽은 방위각이다.** ±15° 부터 무너진다. 2b 의 변 피팅이 행·열 극값을 쓰는
축 정렬 방식이라 판이 회전하면 변을 잘못 잡고, 그 오차는 주기 보정으로도 못 메운다.
→ 회전에 견디는 사각형 검출(회전축 스캔 또는 convex hull 기반)이 다음 과제다.

### 2e 회전 대응 검출 — 방위각이 뚫렸다

덩어리의 2차 모멘트로 **주축을 먼저 구하고, 그 축으로 돌린 좌표계에서** 변을 스캔한다.
행·열 극값을 쓰던 축 정렬 방식이 회전에 무너지던 것을 이걸로 흡수한다.
판이 493×292 라 주축이 안정적이다(정사각형이면 못 쓸 방법이다).

| 경사 / 높이 / 방위 | 낱말 | 블록 | 2d 때 |
|---|---|---|---|
| 45° / 400 / **+15** | 가지 ✓ | 4/4 | ✗ |
| 45° / 400 / **−15** | 가지 ✓ | 4/4 | ✗ |
| 45° / 400 / **−25** | 가지 ✓ | 4/4 | ✗ |
| 40° / 450 / +25 | 가쟈 ✗ | 2/4 | ✗ |
| 40° / 400 / 0 | 가지 ✓ | 4/4 | ✓ |
| 50° / 350 / 0 | 가지 ✓ | 2/4 | ✓ |
| 45° / 350 / 0 | 가지 ✓ | 2/4 | ✓ |
| 35° / 400 / 0 | 가지 ✓ | 2/4 | ✓ |
| 30° / 450 / 0 | ✗ | 1/4 | ✓ (퇴행) |

**방위각 3/4 성공** (2d 는 0/3). 낱말 기준 10개 중 7개.

⚠️ **30°/450 이 퇴행했다.** 낮은 각도에서는 판이 납작해 보여 주축 추정이 흔들리는 것으로
보인다 — 확인한 것이 아니라 추정이다. 조건별로 오락가락하는 구간이 남아 있고,
그것이 다음에 좁힐 대상이다.

### 3단계 채점 하네스 — 300 조합 스윕

경사각 10 × 높이 6 × 방위각 5 = **300 조합**을 자동으로 돌려 낱말 일치를 잰다.
정답이 있으니 채점이 공짜다. 한 번에 약 20초.

**191/300 (64%) 성공.** 그리고 손으로 재던 표본과 그림이 달랐다.

| 경사각 | 성공 | | 방위각 | 성공 |
|---|---|---|---|---|
| 20° | 0/30 | | 0° | 44/60 |
| 25° | 1/30 | | −15° | 42/60 |
| 30° | 7/30 | | +15° | 39/60 |
| 35° | 14/30 | | −30° | 39/60 |
| 40° | 25/30 | | **+30°** | **27/60** |
| 45° | 26/30 | | | |

🔴 **55° 이상이면 방위각 ±30° 까지 100%다.** 40~50° 는 83~93%, 35° 이하는 급락한다.
손으로 「35°/400 성공, 30°/450 실패」 같은 점을 몇 개 재던 것이 전체를 못 보여주고 있었다 —
그래서 2e 에서 「30° 퇴행」을 우연히 발견했고, 그게 사실은 35° 이하 전체가 불안정한

⚠️ **방위각 +30 만 27/60 으로 유독 나쁘다**(−30 은 39/60). 좌우가 비대칭이니 조명 방향이
의심되지만 **확인한 것은 아니다.** 조명을 흔들어 재면 답이 나온다.

**권고 갱신: 경사 55° 이상. 40° 이상이면 실용, 35° 이하는 쓰지 않는다.**

### 거치대를 판에 붙인다면 — 잠망경 방식 (Osmo 형)

거치대가 판에 붙으면 **경사각·높이·방위각이 사용자 변수가 아니라 설계값**이 된다.
아무 조건에서나 되게 만들 필요가 없고, 우리가 고른 한 조건에서만 되면 된다.
그래서 방위각을 ±10° 로 좁히고 다시 쓸었다.

🔴 **그런데 여기서 하마터면 크게 틀릴 뻔했다.** 264 조합 중 262 가 「성공」으로 나왔는데,
**그중 150 이 폴백**이었다 — 판 검출에 실패해 정답 좌표로 물러선 것이라 실전에서는
불가능한 성공이다. 실제 검출로 성공한 건 112 뿐이었다.

| 높이 | 실제 검출 (FOV 68°) |
|---|---|
| 200~275mm | **0/24** |
| 300mm | 3/24 |
| 350mm | 10/24 |
| 375mm | 20/24 |
| 400~500mm | 24/24 |

**일반 화각으로는 높이 400mm 이상이어야 판이 화면에 다 들어온다.**
판이 493×292mm 로 크기 때문이다.

이건 잠망경 방식과 정면으로 부딪힌다. Osmo 처럼 반사경으로 시야를 꺾으면 카메라 높이가
태블릿 높이(~200mm)로 낮아지는데, 그 높이에서 493mm 를 담으려면 화각이 **101°** 필요하다.

**→ 초광각 카메라를 쓰면 된다.** 요즘 폰은 110~120° 초광각을 갖고 있다.

| 화각 | 검출 (높이 150~300mm) |

| 68° (일반) | 0/24 |
| 90° | 5/24 |
| 105° | 11/24 |

|---|---|---|---|---|---|---|
| 60° | − | − | 검출만 | ✓ | ✓ | ✓ |
| 70° | − | − | ✓ | ✓ | ✓ | ✓ |
| **80°** | − | **✓** | ✓ | ✓ | ✓ | ✓ |
| 90°(수직) | − | − | − | − | ✓ | ✓ |

🔴 **거치대 설계 사양: 초광각 카메라 · 경사 70~80° · 높이 175~250mm · 방위각 ±10°.**
90°(완전 수직)는 판 대각선을 담느라 오히려 더 멀어야 하니 피한다.

⚠️ 폰마다 초광각 화각과 카메라 위치가 다르다. 잠망경이 그 차이를 흡수해야 하고,
기종별 초기 캘리브레이션이 필요할 수 있다.

## 6. 시뮬레이터 — 정답을 아는 무한 테스트 데이터

이게 이 기획의 진짜 값어치다. **3D 보드는 이미 블록이 어디에 어느 방향으로 있는지
정확히 안다**(`placed` 배열). 그 상태로 카메라를 폰 위치에 놓고 렌더하면,
**정답이 딸린 카메라 영상**이 공짜로 나온다.

### 흔들 파라미터

| 축 | 범위 | 이유 |
|---|---|---|
| 경사각 | 15° ~ 90° | 거치대 종류 |
| 높이 | 20 ~ 50cm | 책상 거치대 |
| 방위각 | ±30° | 판을 정면으로 안 놓음 |
| 조명 방향·세기 | 여러 각 | 그림자가 획을 먹는지 |
| 색온도 | 2700K ~ 6500K | 백열등 ~ 주광 |
| 렌즈 왜곡 | 0 ~ 중간 | 광각 폰 |
| 노이즈·모션블러 | 0 ~ 중간 | 흔들리는 손, 어두운 방 |
| 가림 | 손 모형 0~2개 | 아이가 놓는 중 |

### 자동 채점

각 조합마다: 렌더 → 인식 → `placed` 와 대조.

| 지표 | 뜻 |
|---|---|
| 블록 검출률 | 놓인 블록 중 몇 개를 찾았나 |
| 위치 정확도 | 칸 단위로 정확히 맞췄나 |
| 자모 정확도 | 회전까지 포함해 맞췄나 |
| **낱말 일치율** | 최종적으로 같은 글자가 나왔나 |

낱말 일치율이 최종 지표다. 블록 하나를 놓쳐도 낱말이 맞으면 아이에겐 문제가 없고,
반대로 자모 하나를 헷갈리면 낱말이 통째로 틀린다.

산출물은 **경사각 × 높이 히트맵** — "어느 거치 조건에서 되는가"를 한 장으로 답한다.

## 9. 지금 정해야 하는 것 (사출 전)

카메라 인식으로 가면 **판과 블록의 물리 사양이 인식 성능을 좌우**한다.
설계 변경이 가능한 시점에 정해야 할 것들:

1. **판 표면 무광** — 반사가 격자를 지운다
2. **블록 2색의 채도를 높게, 색상환에서 멀게** — 판(무채색)과 분리
3. **블록 옆면과 윗면의 명도 차** — 두께 8mm가 그림자를 만든다. 이건 오히려 도움
4. **판 테두리와 놀이 영역의 명도 차** — ① 단계 검출이 여기 달렸다

## 10. 열린 질문

- 인식을 **실시간(프레임마다)** 으로 할지, **셔터(다 놓고 버튼)** 로 할지.
  실시간이 자연스럽지만 손 가림 문제가 커지고 배터리를 먹는다. 시뮬레이터로 답할 수 있다.
- 블록이 판 밖(책상)에 있어도 읽을지. 지금 3D는 판 안에서만 논다.
- 판을 안 쓰고 **책상 위에 블록만** 놓는 것도 되나 — 그러면 판조차 필요 없다.
  격자라는 기준이 사라져 훨씬 어렵지만, 제품이 통째로 달라진다.

## 11. 실물 형상·잠망경·거치 (2026-08-28)

시뮬레이터를 실물에 맞춰 다시 세웠다. `/tango-board-3d.html`(editor2 TopBar 🧩 탱고HW).

### 🔴 시뮬레이터가 정답을 알면 안 된다

가장 큰 결함이었다. 판 검출에 실패하면 **정답 네 점으로 warp** 하고 있었다.
폰에는 없는 능력이라 판이 화면 밖으로 134% 나가도 낱말이 읽혔고,
그동안의 「자모 31/33」은 실물 성능을 뜻하지 않았다.

- 못 찾으면 아무것도 읽지 않는다(「판이 안 보여요」). 정답 좌표는 채점(`cornerErr`)과
  디버그 체크박스 전용.
- 화면 낱말도 판 직독이 아니라 **카메라가 읽은 것**을 띄운다.
- 일반화: 시뮬레이터의 폴백은 곧 거짓 성공률이다. 「성공」을 실물이 할 수 있는 일로만 정의할 것.

### 형상 — NX 에서 뽑은 그대로

`.prt` → 내장 JT 스트림 → jcadlib(세그먼트 타입 패치) → 정점 CSV(mm) → `tango-board-3d.mesh.json`.

- 블록 = **몸통 8mm + 윗면 인서트 1.5mm** 3피스. 몸통만 쓰면 윗면 78% 가 파여 보인다.
  인서트를 합치니 템플릿 IoU 도 올랐다(ㅂ 0.909→0.959, ㄹ 0.963→0.982).
- 실물 메시 22/23종(ㅉ 은 세트에 없다).
- 획 두께 **0.47칸(6.9mm)** — 거리변환과 IoU 스윕이 같은 값. **ㅣ 만 1×5칸·0.38**.
- 🔴 **블록 외곽 ≠ 획 두께.** 부품 폭 10.6mm 를 획으로 넣었다가 인식이 31→29 로 떨어졌다.
- 🔴 **JT 추출은 작은 세그먼트까지.** 18KB 이상만 뽑아 813개 중 596개를 건너뛰었고,
  ㅣ 몸통과 인서트 7종이 거기 있었다. 획이 단순한 부품일수록 세그먼트가 작다.

### 잠망경 — 화각을 정하는 건 렌즈가 아니라 거울

폰 뒷면 카메라 앞에 45도 근처 거울을 세운다(Osmo 형). 반사 법칙에서:

    d' = -back·cos(2μ) - up·sin(2μ)
    내려다보는 각 = 태블릿 기울기 + 2μ - 90        μ = 거울과 태블릿 면이 이루는 각

- **거울 1도 = 시선 2도.** 공차가 두 배로 증폭된다.
- 들어오는 빛은 거울 구멍만큼이고, 거울이 시선에 대해 기울어 있어 **세로가 cos(μ) 만큼 준다**.
  25×20mm @15mm → 60×75°(렌즈 68×84° 를 거울이 제한).
- 그래서 시뮬레이터는 하향각을 입력받지 않는다 — **거울 각도에서 파생**한다. 실물에서
  사람이 정하는 것도 거울 각도다.

### 거치 기본값 (판 500×315)

    좌우   격자 정중앙 x=185mm     앞뒤   판 뒤 가장자리에서 15mm
    패드   높이 320mm · 기울기 85°  거울   32° → 하향 59°       코너 오차 0.013

- 🔴 **판에 슬롯을 파서 꽂는 구조는 못 쓴다.** 판 뒤 가장자리에서 판 폭을 담으려면
  가로 77.8° 가 필요한데 거울이 주는 건 68.5°. Osmo 가 매트를 앞에 따로 두는 이유가 이것이다.
- 🔴 **격자가 판 중앙이 아니다.** 조작판이 있던 오른쪽 자리가 여백으로 남아 24mm 치우쳐 있다
  (왼 21.7 / 오른 69.2mm). → **새 판은 격자를 판 폭 정중앙에.** §9 에 더한다.
- 태블릿을 높일수록 판이 덜 찌그러져 더 가까이서 크게 본다(250mm 28% → 320mm 44%).

### 인식을 막고 있던 것 셋

1. **조작판 좌표 버그** — 렌더는 조작판을 껐는데 놀이 영역은 조작판 포함 좌표로 유도했다.
   좌표가 통째로 밀려 있었다. 고치니 **오차 0.14 → 0.012**.
2. **가장자리 거부** — 판이 화면 가장자리에 한 변만 닿아도 포기했다. 세 변 이상 잘릴 때만
   포기하도록 완화 → **작동 거리 339~520 → 240~520mm**.
3. **거치대가 판 폭 중앙이 아니라 격자 중앙에** 있었다(21mm). 그 차이로 100 조합 전부 실패.

### 다음

- **격자 질감 검출** — 지금은 판 외곽을 찾는다. 격자 바닥 밝기가 베젤과 같아(0.700)
  밝기로는 못 가르니 **핀의 국소 분산**을 봐야 한다. 되면 베젤이 안 보여도 읽으므로
  거치대를 격자 중앙에 두면서 더 가까이 붙일 수 있다.
- **실사 입력은 깔아 뒀다** — 패널의 `🖼 사진 / 🎥 웹캠`. 인식기가 `simTex` 한 장에서만
  픽셀을 받으므로, 그 텍스처를 3D 렌더 대신 실제 그림으로 채우면 검출·warp·분류가
  그대로 돈다(비율 지킨 레터박스 + `UNPACK_FLIP_Y_WEBGL`). 3D 폰 시점을 그대로 뽑아
  사진으로 되먹여 같은 낱말이 나오는 것까지 확인했다.
  같이 붙인 것 = **임계값 슬라이더**(`TUNE` — 색상 회전·채도 하한·밝기 하한·판 밝기)와
  **분류 마스크 미리보기**. 넷 다 돌리면 인식이 깨지고 되돌리면 복구되는 것을 확인했다.
- **실사 검증(§7 4단계)** — 여전히 남아 있다. `classifyPixels` 가 색상각 고정 임계
  (주황 5~60° / 민트 120~190°)로 자모를 가르는데, 실제 카메라는 조명·화이트밸런스로
  색상각이 통째로 밀린다. 실물 사진 한 장이면 드러난다.

## 12. ✅ 실사 검증 완료 — 폰에서 읽는다 (2026-08-30)

§7 4단계(실사 검증)가 끝났다. 사용자 폰(전면 카메라 + 잠망경 거울, 고정 거치)에서
낱말이 읽히고, 읽고 나서 소리까지 나간다. 이 절이 §4·§11 의 「다음」을 대체한다.

### 무엇이 바뀌었나 — 색이 먼저다

§11 이 걱정한 대로 **고정 색상각 임계(주황 5~60° / 민트 120~190°)는 실물에서 밀렸다.**
그래서 순서를 뒤집었다 — 밝기·형상보다 **색을 먼저** 갈라 덩어리를 만든다.

```
입구  사진/웹캠 → photo.ctx.scale(-1,1)   좌우만 되돌린다(반사경). 상하는 camSim.flipY.
  ↓
검출버퍼  긴 변 808px 로 축소 후 readPixels        (한 프레임 28ms — 가장 비싸다)
  ↓
판 찾기  findPlayQuad = 격자(cv) → 격자 → 테두리
  격자(cv) = cvtColor GRAY → GaussianBlur → subtract(blur−gray) → threshold OTSU
             → connectedComponentsWithStats → 규칙적 이웃만 → 기저벡터 → findHomography
  🔴 한 번 찾고 캐시한다. 주기적 재탐색은 그 프레임만 40→323ms 로 튀어 떨림으로 보였다.
     연속으로 못 읽을 때만(latRefindAfter) 다시 찾는다 — 시계가 아니라 증상이 방아쇠다.
  ↓
펴기  cv.warpPerspective → CELL 24px/칸, MARGIN 5칸
  🔴 CELL 16 이면 획 사이 홈이 3px 로 사라져 ㄹ 이 ㅌ 으로 읽힌다(검출버퍼에선 8px).
  ↓
색 분할  classifyPixelsColor (전부 OpenCV)
  cvtColor RGBA→RGB→HSV → inRange(노랑 H20~38 / 초록 H38~85) → morphologyEx OPEN/CLOSE
  → 획 사이 홈 파내기(회색조가 국소평균보다 grooveCut=4 어두우면 뺀다)
  → threshold(1)·threshold(2) → add → 라벨을 cv 안에서 만들어 한 번에 복사
  🔴 이 함수의 catch 는 조용하다. reco.colorInfo.경로 가 '색분할' 이 아니면 옛 경로로 떨어진 것.
  ↓
덩어리  components() — 4이웃, 같은 색끼리만. (손코드)
  ↓
자모 판정  형판 IoU. 1·2위가 tieGap(0.06) 안이면 짝별 판정:
  ㄹ/ㅌ = cv.matchTemplate(이진 마스크, TM_CCOEFF_NORMED)   ㅁ/ㅇ = 모서리 채움
  ↓
조합  parseFree(자음마다 가까운 모음) → voteWord(7프레임 다수결)
```

**분석 한 프레임 437 → 33ms.** 분석 주기 `recoEveryMs 250`(미리보기는 30fps 로 따로).

### 이미 반증된 것 — 다시 하지 마라

| 시도 | 결과 |
|---|---|
| 판의 **구멍/돌기**에 기대기 | 파는 판은 구멍이 없다. 색으로 간다 |
| 상관을 **회색조**로 재기 | 밝은 블록이 밝은 판 위라 대비가 뒤집혀 ㅐ→ㅒ. **이진 마스크**로 |
| 상관을 **주 지표**로 쓰기 | ㅎ 이 ㅌ 을 이긴다(0.418 vs 0.346). IoU 가 고르고 상관은 동점 판정만 |
| ㅁ/ㅇ 을 상관으로 가르기 | 0.561 vs 0.579 로 못 가른다 → 모서리 채움(0.55 vs 0.06) |

🔴 **형판 둘이 같으면 어떤 판정법으로도 못 가른다.** ㅐ/ㅔ 겹침이 1.000 이었고,
고칠 곳은 판정이 아니라 **도면**이었다 — 실물엔 ㅔ 조각이 없다(돌기가 바깥인 ㅓ + ㅣ).

ㅐ/ㅔ 1.000 · ㅒ/ㅖ 0.996 · ㄹ/ㅌ 0.925 · ㄷ/ㅁ 0.847 · ㅌ/ㅍ 0.767 · ㅁ/ㅇ 0.742.

### 학습 화면

시작화면에서 **시뮬 / 카메라**를 고른다. 카메라 모드는 **두 글자 낱말카드가 가운데**,
인식 화면과 OpenCV 사각형은 오른쪽 아래 작게. 낱말카드 옆에 「다른 낱말」 버튼.

- **바뀐 음절만 읽는다** — 전체를 다시 읽으면 블록 하나 올릴 때마다 앞 글자까지 들려
  방금 놓은 게 뭐였는지 묻힌다. 정답을 맞추면 그때 전체를 읽는다.
- 칭찬 = **앱 독후활동과 같은 문구·호리·색종이**(`prefers-reduced-motion` 존중).

### 읽어주기 지연 — 기다림 두 겹 + 다운로드

「인식은 빠른데 읽어주는 게 느리다」의 원인은 계산이 아니었다.

```
다수결 넘어가기   4프레임 × 250ms = 1.00초   ← 화면 글자는 여기서 뜬다
안정 대기         4프레임 × 250ms = 1.00초   ← 다수결이 이미 한 일
음절 mp3 받기                      0.65초   ← 프리워밍은 자모만 데웠다
                                  ───────
                                    2.65초
```

🔴 **같은 평활화를 두 겹으로 하면 지연만 두 배가 된다.** `autoSpeak` 은 `voteWord` 를
거친 낱말을 받는데 거기서 또 네 번을 기다렸다 → `SAY_STEADY 2`.
🔴 **음절 mp3 는 임계 경로에서 뺀다.** 다수결 **전의 날 인식 결과**로 미리 받으면
다수결이 굳기 전에 받기가 끝난다(총 다운로드량은 그대로). 낱말카드 두 글자도 카드가 뜰 때.
→ **2.65 → 1.5초.** 🔴 여기서 더 줄이지 말 것 — 더 낮추면 중간 낱말을 지껄인다.

### ㄹ/ㅌ — 상관은 이 짝을 못 가른다 (2026-08-30 저녁, 사용자 프레임)

「ㅌ 을 ㄹ 로 읽는다」가 올라왔고, 같은 프레임이 다음 번엔 맞았다. 흔들림의 전형이다.
그 프레임에서 잰 상관 여유는 **0.0013(0.56%)** — 판정이 아니라 동전던지기였다.

마스크를 그려 보니 이유가 나왔다. 홈이 24행 중 **1행**밖에 안 파여 채움률이 0.824,
사실상 통짜 네모다. 상관은 전체를 한 숫자로 뭉개므로 그 1행이 묻힌다.

```
행 9  .#####..................   ← 위칸 홈. 왼쪽 기둥만 남았다 = ㅌ
행 10 .#####.###.############.
행 17 .#####..................   ← 아래칸 홈. 역시 왼쪽 = ㅌ
```

🔴 **정보는 사라지지 않았다. 한 행에 몰려 있었을 뿐이다.** 도면을 보면 가로막대 셋은
둘이 같고 다른 건 **위칸 기둥 위치 하나뿐**이다 — ㄹ 은 오른쪽(x=2.5), ㅌ 은 왼쪽(x=0.5).
그래서 `upperGapSide(comp, W)` 를 만들었다: 위 절반에서 **가운데가 가장 비어 있는 줄**을
찾고(=위칸 홈), 그 줄의 **왼쪽 20% 채움 − 오른쪽 20% 채움**을 돌려준다.

| 표본 | 실제 | 위칸 좌−우 | 상관차(ㅌ−ㄹ) |
|---|---|---|---|
| `_t1`(사용자 프레임) | ㅌ | **+0.85** | +0.0013 ⚠ |
| `_ph1` | ㅌ | +0.85 | +0.0265 |
| `_ph2` | ㅌ | +0.84 | +0.0366 |
| `_ph3` | ㅌ | +1.00 | +0.1658 |
| `_ph4` | ㅌ | +0.92 | +0.0293 |
| `_ph5` | ㅌ | +0.85 | +0.0546 |
| `_w1`(재펠 받침) | **ㄹ** | **−0.84** | −0.0844 |
| `_k2`(껍질 받침) | **ㄹ** | **−0.53** | −0.0947 |

**ㅌ 6개 최소 +0.84 · ㄹ 2개 최대 −0.53 → 겹침 0, 간격 1.37.** 문턱 ±0.30 으로 결정하고,
홈이 안 파여(가운데 채움 > 0.35) 할 말이 없으면 **예전대로 상관**으로 떨어진다.

🔴 **이 자는 ㅁ/ㅇ 의 모서리 채움과 같은 성격이다** — 짝을 실제로 가르는 자리가 어디인지
도면에서 찾아 **거기만 잰다**. 상관·IoU 처럼 전체를 요약하는 자는 5.9% 차이를 못 본다.
🔴 **양쪽 표본에서 다 재고 만들었다** — ㅌ 만 재고 규칙을 만들어 틀린 전례가 있다.

### 남은 것

- **판 사각형이 프레임마다 흔들린다.** 같은 사진인데 격자(cv)로 찾으면 못 읽고
  테두리로 찾으면 읽는 경우가 있다(`_t1`·`_w1`). 축척이 어긋나면 형판이 안 맞고
  마스크도 통짜가 된다 — 위 ㄹ/ㅌ 문제의 **뿌리도 여기일 가능성이 크다**.
- **홈이 한 행밖에 안 파인다.** `grooveCut`·`CELL` 을 더 볼 여지가 있으나,
  🔴 **잘 되고 있을 때 만지면 어디서 나빠졌는지 가릴 수가 없다.** 증상이 먼저다.

한때 「남은 문제」로 적어 뒀다가 **폰에서 재현되지 않은** 것 둘 —
①가로로 붙여 놓으면 못 읽는다(초록이 36~40°로 내려앉아 경계 38° 를 넘던 프레임이 있었다)
②껍질의 받침 ㄹ(판 찾기가 흔들려 마룻바닥 블록까지 16개를 읽던 프레임).
지우지 않고 남긴다 — 다시 나오면 여기서부터 본다.
