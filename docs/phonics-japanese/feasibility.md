# 일본어(가나) 파닉스 타당성 조사

> 2026-08-05 · **조사 리포트** (빌드 아님). "만들 수 있는가 / 어떻게 만드나 / 무엇이 걸림돌인가"만 판단.
> 코드 미변경. 결정표(§4)는 착수 전 사람과 합의 항목.

## 0. 한 줄 결론

**만들 수 있다. 한글·영어보다 오히려 쉽다** — 가나가 "글자=소리" 1:1 모라 음절 문자라 한글의 자음+모음
조합(blend)도, 영어의 CVC 블렌딩도 없다. 학습 단위가 **한글 모음 단원**(글자 하나 = 소리 하나, 눌러 듣고
쓰기)과 거의 같고 blend 계열 활동을 통째로 뺀다. **가장 큰 비용은 코드가 아니라 콘텐츠 저작**(오십음도
커리큘럼 + 단어 카드 이미지)이고, **가장 큰 미결정은 타겟 학습자**(일본 아이 native vs 한국 아이 L2)다.

### 1.3 음원 경로 — 여기가 핵심 판단

한/영은 R2 라이브러리 카테고리 `mod_korean`·`mod_english`·`mod_phonics`(`PhonicsAudioCategory`,
`shared/types/storybook.ts`)에서 낱소리를 직행으로 뽑고, 공백 있는 이어읽기만 서버 `concat` 한다.

**가나는 blend 가 없어 concat 이 사실상 불필요하다** — 각 모라(か·き·に…)가 이미 온전한 발화 단위다.
그래서 두 갈래:

- **(권장) 사전 녹음 라이브러리 직행** — 기본 46 + 탁음/반탁음 25 + 요음 33 ≈ **104 클립**을 한 번 구워
  R2 `mod_japanese`(신규 카테고리)에 올리고, 한글 `getKoreanSyllableUrl` 과 대칭인 `getJapaneseMoraUrl`
  로 직행. **첫 소리 지연 0, 성공음 통일, 서버 부하 0**. 한글이 시행착오 끝에 도달한 정답 경로다.
  - 이때 손대는 서버 코드: `PhonicsAudioCategory` 에 `mod_japanese` 추가 · `phonics-library.service.ts`
    의 `parseKey` 정규식·`downloadSound` 우선순위·`list()` 결과 3필드 → 4필드 · 클라 `resolveTtsUrl`
    언어 유니온(`'korean'|'english'|'vi'|'zh'|'th'`)에 `'japanese'` + 직행 분기. 전부 **작은 diff**.
  - 🔴 `parseText` 의 한글 음절 분해 정규식(`[가-힣]`)은 가나를 안 쪼갠다 → 라이브러리 직행이면
    애초에 concat 을 안 타므로 무관. concat 을 쓸 일(요음 이어읽기 등)이 생기면 그때 가나 split 추가.
- **(대안) 런타임 TTS** — Gemini `ja-JP` 준비돼 있으나 🔴 **memory 상 Gemini TTS 는 짧은 CJK/타이에
  무응답 이력**(`multilingual-vocab-games`·gemini-tts 주석). 낱 모라 "き" 는 1글자라 정확히 그 위험대.
  Google TTS 는 Chirp3-HD 가 짧은 것에 강하나 `VOICE_BY_LANG` 에 **ja 항목이 없어** 추가 필요. →
  어느 쪽이든 **104 클립을 한 번 구워 라이브러리로 박는 게 안전**(품질·지연·비용 다 이김).

## 2. 일본어 파닉스의 언어학적 설계 (웹 조사)

출처: Wikipedia *Gojūon* / *Hiragana* (Jina Reader 로 본문 확인).

### 2.1 근본 차이 — 가나는 "파닉스"가 아니라 "음절 문자 리터러시"

알파벳 파닉스는 **음소를 낱글자에 대응**시켜 blending(c-a-t)으로 낱말을 조립한다. 한글도 자음+모음을
음절로 **합친다**. **가나는 합치지 않는다** — 각 가나 = 1 **모라(mora)** = 하나의 온전한 소리(か = /ka/).
"글자=소리"가 거의 완전 1:1이라, 학습은 **blending 이 아니라 글자-소리 짝 암기 + 낱말 읽기**다.
→ 앱 관점에서 **한글 「모음 배우기」 단원**(글자 하나 눌러 듣고 쓰기, blend 없음)이 정확한 원형.

### 2.2 오십음도(gojūon) 구조 — 커리큘럼 뼈대

전통 정렬 = 5모음 × 10행(자음) 격자. 실제 46자(빈칸 5 + ん 1).

```
     a    i    u    e    o
∅    あ   い   う   え   お        ← あ行 (모음)
k    か   き   く   け   こ        ← か行
s    さ   し   す   せ   そ        (し=shi, す 예외 발음)
t    た   ち   つ   て   と        (ち=chi, つ=tsu)
n    な   に   ぬ   ね   の
h    は   ひ   ふ   へ   ほ        (ふ=fu)
m    ま   み   む   め   も
y    や   —   ゆ   —   よ         ← 3자 (yi·ye 없음)
r    ら   り   る   れ   ろ
w    わ   —   —   —   を          ← わ·を 2자 (ゐゑ 폐기)
     ん                            ← 격자 밖 단독 자음
```

**커리큘럼 = 행 단위 유닛** 이 자연스럽다: 한 유닛 = 한 행(3~5자). 46자를 10~11 유닛으로.
이건 한글1이 「자음 단원」을 자음별로 쪼갠 것과 같은 구조 — **유닛당 한 소릿결(row)**.

### 2.3 확장 가나 (탁음·요음·촉음·장음) — 범위가 곧 결정 항목

| 종류 | 표기 | 예 | 수 | 4~5세 난이도 |
| --- | --- | --- | --- | --- |
| **탁음 dakuten** ゛ | 청음→유음 | か→が, さ→ざ, た→だ, は→ば | 20 | 낮음(같은 글자에 점) |
| **반탁음 handakuten** ゜ | h→p | は→ぱ | 5 | 낮음 |
| **요음 yōon** | +작은 ゃゅょ | き+ゃ→きゃ (kya) | 33 | 중간(2글자=1소리) |
| **촉음 sokuon** | 작은 っ | さっか (sakka, 겹자음) | — | 높음(소리 없는 글자) |
| **장음 chōon** | 모음 겹침 / ー | おかあさん · らーめん | — | 높음(추상) |

→ **기본 46(±ん)만으로 한 라인이 성립**하고, 탁음/반탁음까지가 유아 상식선. 요음·촉음·장음은
**뒤 레벨 또는 보류**가 합리적(한글이 복잡한 모음·받침을 뒤 레벨로 뺀 것과 같은 판단). 착수 전 합의.

### 2.4 히라가나 vs 가타카나

일본 유아는 **히라가나 먼저**(고유어·조사), 가타카나는 나중(외래어). 둘은 1:1 대응(같은 소리, 다른 글자).
→ **히라가나 우선 라인**이 정석. 가타카나는 별도 레벨/책으로 미룰 수 있다(공수 사실상 2배 아님 — 같은
음원·같은 커리큘럼 뼈대에 글자 자산만 교체). 착수 전 합의.

### 2.5 일본 현지 유아 학습법

**あいうえお表**(aiueo 표) = 오십음도 벽 포스터를 눌러/짚어 소리 내고, **글자↔그림 낱말 연상**
(あ→あり 개미, い→いぬ 개, う→うし 소)으로 익힌다. 촉음·장음보다 **낱말 통독**이 먼저 온다. 이건
앱의 「글자 사냥」(오십음도에서 목표 가나 찾기)·「듣고 고르기」(모라 소리→낱말 그림)·단어 카드 게임과
**정확히 겹친다** — 활동 설계를 새로 발명할 필요가 없다.

### 2.6 타겟 학습자 — 두 시나리오 (착수 전 반드시 결정)

| | **A. 일본 아이 (native 리터러시)** | **B. 한국 아이 (L2 일본어)** |
| --- | --- | --- |
| 대응 선례 | 한글 파닉스(모국어 문해) | **영어 파닉스**(한국 아이가 영어 배움) |
| 지시·안내 음성 | 일본어 | **한국어**(현행 영어 파닉스와 동일 — "무엇을 하라는 말은 아이 말로") |
| 화면 UI 언어 | ja (🔴 파닉스 모듈 i18n 미착수 → 이 시나리오는 **i18n 선행** 필요) | ko (현행 그대로, 하드코딩 유지 가능) |
| 낱말 선정 | 일본 유아 어휘(あり·いぬ) | 한국 아이가 아는 쉬운 일본어 낱말 + 필요시 뜻 |
| 가타카나 | 필수(후속) | 선택 |
| 전략 적합성 | 해외 ja 오픈(overseas 플랜)과 정렬 | **현행 제품(한국 아이 대상)의 자연스러운 확장** |

🔴 이 갈림이 코드·콘텐츠·i18n 을 전부 가른다. **영어 파닉스가 B(L2) 형태**라 기존 제품에는 B 가
1:1로 맞물리고, A 는 파닉스 모듈의 **deferred i18n 작업**(화면 한국어 100여 개·안내 음성 `-ko` 하드코딩)을
먼저 깨야 한다. 에이전트가 추측하지 않고 사람에게 묻는다.

## 3. 타당성 결론

### 3.1 난이도·공수 (한글·영어 대비 재사용 %)

| 축 | 재사용 | 비고 |
| --- | --- | --- |
| 데이터 스키마/타입 | ~90% | 같은 커리큘럼 shape, blending 비움 |
| 활동 컴포넌트 | ~70–80% | listen/write/hunt/word-choose/게임4 그대로. **blend·CVC 통째 삭제**(가나엔 없음) → 오히려 뺄 게 많다 |
| 음원 인프라 | ~60% | 라이브러리 직행 경로 재사용, **클립 104개**만 신규(한글 3232 대비 극소) + 서버 카테고리 1개 |
| `splitUnits`/블록·쓰기 게임 | ~95% | 코드포인트 분해가 가나에 맞음 |
| 단어 카드 → 게임 연동 | ~90% | rembg keypoints·link 스크립트 그대로 |
| **커리큘럼·단어 카드 콘텐츠** | **0% (신규 저작)** | **최대 비용** — 오십음도 유닛 + 유닛당 낱말 4개 + 카드 이미지(사용자 GPT 생성). 한글 나무 32유닛·ABC 나무 39유닛과 같은 저작 파이프라인 |
| 폰트·안내음성 | 소 신규 | Noto JP 1줄 + 안내 클립 몇 개 |

**총평: 코드 난이도는 한/영보다 낮다**(blend 없음 = 가장 버그 많던 TTS 체인·합체 애니메이션이 빠진다).
**총 공수는 콘텐츠 저작이 지배**하며, 그 규모는 한글 나무 라인 1개(유닛 ~11 + 카드 ~50)와 비슷하거나 작다.

### 3.3 걸림돌

1. **타겟 미결정(#1)** — 최우선. A면 파닉스 i18n 선행이라 착수 범위가 크게 다르다.
2. **커리큘럼·단어 카드 콘텐츠 저작** — 코드가 아니라 사람+이미지 생성 비용. 가나 낱말 선정
   (유아 어휘)·카드 388장식 파이프라인. 가장 오래 걸린다.
3. **가나 음원 품질/지연** — 라이브러리 직행으로 우회 가능하나, **104클립 최초 생성 시 낱 모라 발음
   품질을 반드시 실측**(Gemini 짧은 CJK 무응답 이력 → Google Chirp3-HD ja 보이스 추가 또는 성우 녹음).
4. **Japanese 폰트 미등록** — 유아용 가독 글꼴 필요(현 폴백은 한국어 글꼴이라 가나 자형이 어색할 수 있음).
   조용히 폴백되므로(에러 없음) 팔레트 램프·`max-*` 함정과 같은 부류 — 착수 시 실기기 확인.
5. **요음 타일 단위** — きゃ 를 "한 소리 두 글자"로 가르칠 때 `splitUnits`/블록 게임이 코드포인트로
   き·ゃ 를 쪼갠다. 요음까지 범위에 넣으면(#4) 그 한 곳만 커스텀 결합 필요(태국어 grapheme 선례).
6. **plan 미등록 = 죽은 코드** — 한/영에서 반복된 함정. 유닛·활동을 만들면 **그 날 커리큘럼 generator +
   호스트 분기 + 랜딩 카드**까지 한 번에 도달 가능하게(빌드 단계 체크리스트).
