너는 **탱고블록**(카메라로 읽는 한글 레고 블록 판) 인식 담당이다.
사용자가 「탱고블록」이라고 부르는 것 = `tango-board-3d.html?board=lego` 의 인식부다.

## 0. 왜 이 에이전트가 있나 (읽고 시작할 것)

2026-09-07, 판을 초록으로 바꾸고 흰 모음을 추가한 프레임 한 장을 고치는 동안 내가 한 짓:

1. **`find_plate()` 를 새로 지었다** — 배포본 주석에 「판을 찾으려던 길에서 하루를 썼는데 그 중
   어느 것도 답에 필요하지 않았다」고 적혀 있는 바로 그 길.
2. **「판 찾기가 죽어서 전경이 안 돌았다」고 진단했다** — 레고 경로는 판을 안 찾는 게 설계다.
   화면의 `판 못찾음` 은 탱고 경로 필드가 그냥 찍히는 것이다.
3. **`legoCutWalls` 를 빼먹고 이식했다** — 이미 짜여 있고 왜 필요한지까지 주석에 있었다.
4. **무효한 조명 시험으로 틀린 결론을 냈다** — HSV 채도는 노출 배수에 원래 불변인데
   노출 배수만 먹여 놓고 「옛 방식이 더 튼튼하다」고 보고했다.

넷 다 **파일 안 🔴 주석에 이미 적혀 있었다.** 안 읽고 시작해서 그렇다.
그래서 규칙 하나: **코드를 고치기 전에 그 함수의 🔴 주석을 먼저 읽는다.**

## 1. 확정 사실 (실측으로 선 것 — 뒤집으려면 새 실측이 있어야 한다)

### 파이프라인 (`packages/client/public/tango-board-3d.html`, 배포 = 이 파일 그대로)

`?board=lego` → `recognizeLegoDirect()` (live) → 다음 순서다.

```
legoRectify()      🔴 **워프는 기본이 꺼져 있다**(`legoRectifyOn: 0`) — 아래 표 참조.
                   꺼져 있으면 `legoCellSweep` 만 부르고 바로 돌아온다: 띠 12개(8%씩)의
                   돌기 주기(자기상관) → Theil–Sen **직선 cell(y)** → `{lo, mid, at(y)}`.
                   관문·자르기는 덩어리마다 `cellAt(y)`, 커널은 `lo`(가장 작은 칸).
                   켜져 있을 때만 예전의 두 띠(28~36%·60~68%) + 호모그래피를 쓴다.
전경                chroma 한 채널 Otsu + 밝기 바닥(legoVMin)
legoCutWalls()     덩어리마다 V 히스토그램 Otsu → **밝은 쪽(윗면)만** 남긴다.
                   밝은 쪽이 25% 미만이면 안 건드린다.
닫기 → 열기         🔴 닫기가 먼저다. 광택 줄이 획을 세로로 가르므로 먼저 메워야 한다.
연결성분 → splitLego → 형판 IoU → parseFree
```

- **🔴 판을 안 찾는다. 격자도 안 세운다.** 필요한 건 자모의 모양과 상대 위치 둘뿐이다.
- 가짜(가구·바닥·옆 판)는 **덩치와 자리**로 거른다 — 칸 크기로 거르면 안 된다(원근 때문에
  같은 판 안에서도 칸이 37~48px 로 벌어져 멀리 놓인 진짜 글자가 이상점이 된다).
- `legoMaxBlob: 20` 칸 초과는 글자가 아니다.

### 속도 (2026-09-07 실측 — 배포본을 헤드리스 크롬에서, 올라온 프레임 6장 × 13회)

사용자 「인식은 잘하는데 속도가 느리다」. 느낌 = ①한 프레임 계산 + ②다수결 대기 + ③음원.

```
① 한 프레임(데스크톱, 칸 34 프레임 「가」)  전 120ms → 후 100ms
   닫기+열기 35 · cvtColor×4 18 · splitLego 16 · 연결성분×2 10 · legoCutWalls 9(안에 연결성분 1회)
   legoRectify 31 → 3   ← 🔴 워프를 굽고 버리고 있었다(아래)
   matchLegoShape 는 37~275회 불려도 1~4ms — 비트셋이라 싸다. parseFree 0.
② 다수결: readBoard 는 레고도 같은 길이다 — voteWord(WORD_HIST 7) 에서 새 낱말이
   이기려면 4프레임, autoSpeak(SAY_STEADY 2) 가 1프레임 더 = **5프레임**.
   간격은 max(recoEveryMs 250, ①) 이라 데스크톱 1.25초. 폰에서 ①이 250 을 넘으면
   그 초과분이 **×5** 로 느껴진다.
③ 음절 mp3 14~17KB, R2 콜드 0.65초(TTFB) — warmSound 가 다수결 전 날값으로 미리 받으므로
   보통 0. 캐시가 빗나가면 0.65초.
```

- 🔴 **`legoRectifyOn: 0` 인데 `warpPerspective` 를 매 프레임 돌리고 버렸다**(최대 1600px).
  한 프레임의 12~59ms(약 1/4). 끔 검사를 워프 **앞**으로 올렸다(886f8d6e) — 앞선
  간격·줄수·크기 검사는 그대로 거쳐 돌려주는 칸 값이 같다. 여섯 프레임 낱말 전부 동일.
- 🔴 **폰의 ①은 못 쟀다.** 하네스는 데스크톱이고 `grabDetect`(readPixels)는 SwiftShader 라
  100~200ms 로 찍히지만 그건 소프트웨어 래스터라이저 값이라 증거가 아니다. 그래서
  진단 오버레이 「레고 {...} · Nms」에 `reco.ms` 를 찍게 했다 — **다음 📤 의 `s*.jpg` 에
  폰 숫자가 있다.** 그 값이 250 을 넘는지가 다음 판단의 전부다.
- 남은 큰 항목은 닫기+열기(열기가 아직 타원 커널)와 cvtColor 4회 — 둘 다 마스크에 닿는다.
  정확도가 좋은 지금은 건드리지 않는다.
- 하네스(`scratchpad/time_lego.mjs`, puppeteer) 함정 셋:
  `cv.*` 를 감싸면 `Object.assign(wrapper, orig)` 로 embind `overloadTable` 을 옮겨야 한다
  (안 하면 `hasOwnProperty of undefined`) · 정지 사진은 draw 가 한 번뿐이라
  `setInterval(invalidate, 33)` 을 직접 돌려야 분석이 이어진다 · 올라온 `p*.jpg` 는
  캔버스로 한 번 되돌려 넣어야 폰과 같은 낱말이 나온다(확인: 「가」 = 폰 s 프레임과 일치).

### 색 (2026-09-07 초록 판 · 노랑 자음 · 흰 모음)

손으로 고른 조각 실측:

```
초록 판    L 57~62   a* −43 (밝은 데 −31 ~ 그늘 −50)   b* −1 ~ +18
노랑 자음  L 53~69   a*  +3                            b* +51 ~ +57
흰 모음    L 84~88   a*  −2                            b* −5 ~ +9
```

- **전경 축 = a\***(`legoChroma: 'a'`). 여백 25 = 판 산포의 6.1배.
- **자음/모음 = b\***(`legoVowelB: 25`). 공짜로 딸려온다.
- 🔴 **b\* 로는 흰 블록이 원리상 안 보인다**(흰 b* = −0.1 = 판과 같다). 회색 판 시절의 축이다.

### 확인된 동작 (2026-09-07 배포 f9e9fbc3, 사용자 실기 확인 「겁나 잘된다」)

```
랴  ㄹ 0.81 + ㅑ 0.92          러  ㄹ 0.80 + ㅓ 0.96
캴  ㅋ 0.70 + ㅑ 0.80 + ㄹ 0.64      ← 셋이 **붙어 있는** 상태
```

붙은 조각은 `legoMinLong` 을 4.2 -> **3.6** 으로 내려서 풀렸다. 자르기는 옳은 자리를
이미 찾고 있었고(ㄹ0.90 + ㅓ0.93) 조각 긴 변이 4.12·3.83칸이라 4.2 에 걸려 **버려지고**
있었다. 형판은 5칸이지만 옆벽 떼고 열기까지 하면 그보다 더 줄어든다.

### 🔴 색 규칙은 못 믿는다 — 갈래로 형판을 제한하지 마라

「자음 노랑 · 모음 흰색」으로 듣고 채도로 갈래를 정해 형판을 반으로 줄였다.
**맞게 읽던 것을 틀리게 만들었다** — 사용자가 「러」를 놓은 프레임은 ㄹ 도 ㅓ 도
노랑이었다(S 217 / 195). 모음이 자음으로 분류돼 자음 형판만 보게 된다.
그리고 **필요하지도 않았다**: 갈래 제한 없이 위 두 낱말 모두 1위였다.

`legoVowelSat` 은 코드로 남아 있으나 **기본값 0 = 꺼짐**. 켜려면 색 규칙이 실제로
지켜지는지부터 재라. 지금은 안 지켜진다.

### 🔴 카메라가 조용히 640×480 으로 떨어진다

`startWebcam` 의 폴백들이 해상도를 아예 안 요구해서, 첫 요청이 한 번 실패하면
폰 전면 카메라 기본값으로 내려간다. 그러면 칸이 38px → 25.5px 가 되어 마스크가
거칠어지고 자모가 통째로 틀린다. `ideal` 은 못 맞춰도 실패하지 않으므로 버릴 이유가
없었다 — 폴백에도 넣어 두었다(f9e9fbc3).

**증상을 눈으로 볼 자리**: 화면 맨 윗줄 `카메라 720×1280`. 480×640 이면 이것이다.

### 🔴 펴지 않는다 (2026-09-07 결정, `legoRectifyOn: 0`)

펴기의 명분은 「칸이 어디서나 같아야 붙은 자모를 칸 경계에서 자른다」였다. 나란히 재 보니
**네 프레임 모두 안 펴는 쪽이 같거나 나았다**:

```
러   펴고 ㅡㅡㅡㄹㅓ (가짜 3)      · 안 펴고 ㄹㅓ 깨끗
랴   펴고 ㅡㅡㅡㄹㅡㅑ (가짜 4)    · 안 펴고 ㅡㄹㅑㅑ (가짜 2)
캴   펴고 ㅏㅕㅠㅡ 전부 틀림      · 안 펴고 ㅋ0.70 ㅑ0.80 ㄹ0.64 셋 다
n2   양쪽 같음
```

- 워프가 금속 레일을 늘려 가짜 `ㅡ` 를 서너 개 만든다.
- 세로 원근을 다 풀지도 못한다 — 4x5칸짜리가 편 뒤에도 **4.1 x 4.6칸**으로 남는다.
- 명분 자체가 안 선다: **캴은 조각이 붙어 있는데 안 펴고 셋 다 읽혔다.**

⚠ 근거가 네 장이다. 붙은 조각이 많은 판에서 자르기가 나빠지면 `legoRectifyOn: 1` 로
되돌리고 `legoWarpOk`(1.15) 검사에 맡길 것 — 켜져 있을 때 편 그림에서 위·아래 주기를
다시 재서 안 맞으면 안 편 그림으로 폴백한다.

### 🔴 판은 **위아래만** 믿어라 (사용자 확인)

거치대에서 **좌우는 잘릴 때도 안 잘릴 때도 있고, 위아래는 무조건 다 보인다.**
그래서 칸을 재는 것도 **가로 띠의 돌기 간격**(지금은 띠 12개의 직선)뿐이다 —
좌우 폭·좌우 모서리·판 실루엣에 기대는 검사를 붙이지 마라.

내가 한 번 「편 그림에서 판이 삼각형이다 = 펴기가 망가졌다」고 했는데, 좌우가 화면
밖으로 흐른 것뿐이었다. 실루엣은 증거가 아니다.

### 🔴 펴기가 됐는지 재는 법 — 같은 자로 다시

`폄:1` 은 **「예외가 안 났다」는 뜻일 뿐** 잘 폈다는 뜻이 아니다. 펴기의 정의가
「위아래 돌기 간격을 같게 만든다」이므로, 검사도 그 자로 한다 — **편 그림에서
위·아래 주기를 다시 재서 같아졌나.** 배음은 접고 본다(`b > a*1.4 면 b/=2`).

실측:

```
ru_p (러)   1.08   읽힘         n2 (480x640)  1.32   틀림
랴          1.09   읽힘         캴            1.25   틀림
```

좋은 것 1.08~1.09 / 나쁜 것 1.25~1.32 로 갈린다. 문턱 1.15 쯤. 어긋나면 편 그림을
쓰지 말고 안 편 그림으로 읽는 편이 낫다(배포본에 이미 그 폴백 경로가 있다).

### 🔴 하네스에 `rectify` 를 반드시 넣어라

안 펴면 원근에 눌려 4x5 칸짜리 ㄹ 이 **133x133px(=1:1)** 로 찍힌다. 그 상태에서
`legoMinLong`(칸) 같은 관문을 재면 전부 헛돈다 — 한 번 그렇게 재고 「자르기가 크기
관문에 걸린다」는 **틀린 진단**을 내놓았다. 펴고 나면 ㄹ 이 4.1x4.6칸에 IoU 0.90 이다
(안 펴면 3.5x3.5, 0.81).

### 조명·그림자 내성 (합성 시험, 프레임 2장 x 20조건)

```
그늘 35/60/75% · 그늘+푸른기        전부 통과   ← 그늘은 판 a* 를 더 음수로 민다
노출 0.45~1.6배 · 저조도+잡음       전부 통과
색온도 따뜻/차가움                  통과
색온도 **더** 차가움 (R0.62 B1.6)   둘 다 실패  ← 유일한 구조적 약점
노출 x2.5 (클리핑)                  절반 실패
                                   19/20 · 17/20
```

차가운 색온도는 모든 화소의 a* 를 음수로 밀어 블록을 판 쪽으로 끌어온다 — a* 축의
정면 공격이라 이 축을 쓰는 한 남는 약점이다. ⚠ **「판 기준 상대 문턱」으로 고치려다
더 나빠졌다**(19→17, 17→16): 색온도도 못 고치고 멀쩡하던 과다노출까지 깨뜨린다.
프레임 전체 Otsu 를 유지할 것.

### 🔴 칸은 숫자 하나가 아니라 y 의 직선이다 (2026-09-07 밤, 「판떼기를 못 읽는다」)

배포 직후 사용자 프레임(판이 화면 아래 70% 까지 차고 ㅈ·ㅁ 이 아래쪽에 앉음)에서 **후보 0**.
배포 전 파일로도 똑같이 0 — 코드가 아니라 **프레임(거치 구도)** 이 달라진 것이었다.

- 원인: `legoRectify` 가 고정 띠 둘(화면 높이 28~36% · 60~68%)에서 돌기 주기를 쟀는데
  아래 띠에 블록이 앉으면 주기가 lag 하한 8 로 무너지고, 배음 접기가 위 띠까지 8 쪽으로
  끌어내려 **칸 6** → `legoMaxBlob`(20칸=120px) 가 글자를 전부 버렸다.
  예전 프레임 둘도 아래 띠가 8 이었는데 `min(pA,pB)` 가 위 띠를 골라 **운으로** 살았다.

   - **형판에 견줄 때는 되돌려 놓고** 재라. 안 그러면 ㄱ 이 ㄴ 으로, ㅏ 가 ㅓ 로 읽힌다.
   - 앱에 도로 먹이면 **두 번** 뒤집힌다. 올라온 프레임으로 한 테스트는 실시간을 대신 못 한다.
5. 🔴 **HTML 을 고쳤으면 백업과 대조해 문법을 확인해라.** 한 줄짜리 검사면 된다.

   node -e "const fs=require('fs');for(const f of ['a.bak.html','a.html']){const h=fs.readFileSync(f,'utf8');const m=[...h.matchAll(/<script(?![^>]*importmap)[^>]*>([\s\S]*?)<\/script>/g)];let s='ok';m.forEach(x=>{try{new Function(x[1])}catch(e){s=e.message}});console.log(f,s)}"

6. 🔴 **프레임이 거치대에서 온 것인지 확인해라.** 손으로 비스듬히 든 사진은 옆벽이 훨씬 많이

## 5. 작업 순서

1. 고칠 함수의 🔴 주석을 **먼저 읽는다.** (`recognizeLegoDirect`·`legoCutWalls`·`classifyPixelsLego`·TUNE 블록)

3. 파이썬 하네스(`read_lego.py`·`read2.py`, 그리고 새 축은 `read_new.py`)로 먼저 잰다 —
   브라우저보다 훨씬 빠르고, OpenCV.js 11MB 를 기다리지 않아도 된다.
   **배포본 로직을 이식할 때는 빠뜨린 단계가 없는지 원본과 나란히 놓고 확인해라**(내가 `legoCutWalls` 를 빠뜨렸다).

6. 고치면서 알게 된 것은 **이 파일 §1/§2 에 즉시 반영한다.** 반증된 것은 뒤집어 적는다.

## 6. 「캴」— 붙은 세 조각은 아직 못 읽는다 (2026-09-07 미해결)

배포본을 브라우저에서 직접 돌려 잰 값이다(하네스 아님):

```
글자 덩어리   하나, 7.9 x 8.3칸 (칸 34)     ->  자르기가 2조각: ㄱ0.50 + ㅏ0.65 = 「가」
자르기 훑기   깊이2·3 x 칼자리2·4·6 x 목0.75·0.95  = 열두 조합 **전부 같은 결과**
옆벽 끄면     3조각이 되지만 글자는 여전히 틀림(ㅛㅓㅏ)
```

🔴 **옆벽 떼기는 주범이 아니다.** 하루에 세 번 틀린 진단을 내놨다 —
「색으로 가른다」→「밝기로 가른다」→「조각을 지운다」. 재 보니:

```
남긴 것 V215 b*+64 · 버린 것 V142 b*+49   (둘 다 노랑 — 색으로 가르는 게 아니다)
노랑 화소의 67% · 흰 화소의 85% 가 살아남는다 (조각을 지우지도 않는다)
흰 ㅑ 는 전경에 멀쩡히 있다 (a* −3, 전경 100%)
```

남은 것은 **자르기가 세 조각을 못 나눈다**는 사실 하나다. 여기부터 다시 시작할 것.

🔴 **하네스로 「된다」고 보고하지 마라.** 같은 프레임에서 파이썬 하네스는 ㄹㅋㅑ 를
   맞추고 배포본은 「가」를 낸다. 입력 그림은 같다(선명도 52 vs 55, 눈으로도 같다) —
   **내 이식본 matcher 가 `matchLegoShape` 와 다르게 동작할 뿐**이다.
   하네스는 가설을 세우는 데만 쓰고, **결론은 브라우저에서 배포본을 돌려 확인**한 뒤에.
   페이지에서 `detBuf` 를 직접 집어 `legoCutWalls`·`splitLego` 를 부를 수 있다.

## 7. 아직 남은 것

🔴 **붙은 세 조각(캴)은 사용자가 「나중에 하자」로 미뤄 두었다**(2026-09-07).
   버린 게 아니다 — 「방법은 좀 있긴 할 텐데 당장 안 되면 나중에」였다.
   먼저 꺼내 들 카드는 **돌기 격자**(아래)다. 급하면 「블록을 붙여 놓지 마세요」로
   안내하는 것도 사용자가 받아들인 선택지다.

- **금속 레일이 `ㅡ`(IoU 0.94)로 읽힌다.** 조명·펴기와 무관하게 랴 프레임에서 계속 붙는다.
  덩어리 걸러내기(덩치·자리) 쪽 일이고 아직 안 건드렸다.
- **차가운 색온도**(R 0.62 / B 1.6)에서 무너진다. a* 축을 정면으로 미는 유일한 변화다.
- **돌기 격자로 읽기**(칸 점유 격자 vs 형판 rows)는 절반 됐다 — `ㅓ` 는 1.00 정확히
  나오는데 `ㄹ` 은 4x5여야 할 격자가 5x5로 잡힌다. 세로 원근 잔차 탓. `grid.py` 에 있다.
- **조합 좌표의 원근** — `items` 의 x·y 가 아직 화면 평균 칸(`med`)으로 나눈 값이라
  위·아래 글자 사이 거리가 최대 25% 부푼다. 칸 직선이 있으니 `x=(x−W/2)/cell(y)`,
  `y=∫dy/cell(y)` 로 펴 넣으면 된다. 오늘 프레임에선 안 걸려 미뤘다(2026-09-07).
- **양산 판의 위·아래 매끈한 띠**(사용자 제안) — 폭이 정해진 무광 띠를 위·아래에 두면
  픽셀 높이로 배율이 나오고 판 경계도 공짜다. 돌기가 없는 띠는 주기를 못 재므로
  「블록 못 올리는 돌기 띠」는 성립 안 한다. 시제품이 오면 그때.
